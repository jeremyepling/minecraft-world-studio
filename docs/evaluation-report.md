# Initial evaluation · November 24, 2026

**Adopt the published MCPFabric release for the local prototype.** A real Codex conversation discovered the server and read the player in Minecraft 26.3 Creative. A second Codex turn inspected the hillside watchtower, identified its overhanging green roof and sent that observation privately inside Minecraft. WorldEdit worked through both the player and console, and a parameterized skill revised the tower. The two largest gaps for day-to-day collaboration are starting a turn from Minecraft and protecting subsequent manual edits. ## Twelve decisions

The final lab uses an authenticated loopback bridge at `127.0.0.1:25639`, disabled discovery, a private SQLite directory and stdio into Codex. The inherited workspace ACL initially allowed other Windows users to read the generated credentials. The installer now restricts the lab's private runtime to its owner, SYSTEM and administrators, and the effective ACL on the credential file was verified. The launcher code itself is trusted project code. Someone able to replace that code could run it with the account that starts Codex. The Studio profile reduces model context. An agent holding the full bridge key and command privileges still has broad authority inside this instance. The native player-administration approval gate was exercised by declining a game-mode change in the client and verifying Creative mode afterward. [Security boundaries](source-review.md) · [Denial and restart](restart-and-approval.json)

| # | Decision |
| --- | --- |
| 1 | **Foundation.** Yes for a local singleplayer lab. The combination of real world reads, framebuffer access, chat and deterministic execution is sufficient to build and revise a structure today. |
| 2 | **Use unchanged.** Yes. Pin MCPFabric 0.10.0, the matching Java release and compatible Node runtime. Scope its connection and SQLite directory to this project. |
| 3 | **Fork.** No fork is justified by the observed work. The gaps concern collaboration and checked execution above the bridge. |
| 4 | **Can Codex communicate in Minecraft?** Yes. An active turn can read chat, send a player-visible `[AI]` message, use the action bar for progress or send a targeted message. The human keeps the Minecraft client open. |
| 5 | **Can Minecraft initiate a Codex conversation?** No supported direct trigger was found in this release. The Claude-specific notification path and ordinary MCP tool calls have different lifecycles. Prototype a small local listener for explicitly addressed player requests. |
| 6 | **Can it invoke WorldEdit?** Yes, unchanged. Use `send_chat({"message":"//..."})` for the current player's WorldEdit state. This shares selection, clipboard and history with the human. A separate console route also worked. On this pinned stack send `///world WorldStudioLab_minecraft:overworld` through `run_command`, then use explicit positions with `///pos1`, `///pos2` and `///set`. Undoing the console edit left the three player-placed bricks intact. The player then undid those three bricks separately. [Console control](console-worldedit.json) · [Independent histories](worldedit-identities.json) |
| 7 | **Best bulk backend?** The preloaded schematic had the lowest measured 100,000-block time, about 74 ms. Four native fills took 158 ms, generated vanilla fills took 156 ms, and console WorldEdit selection plus set took 159 ms. At 1,000 blocks a single fill took about 4 ms. Schematic preparation and disk loading were outside its timed paste. These are single local trials and benchmark different fixed costs. [Timings and method](../benchmarks/README.md) |
| 8 | **Enough JavaScript?** Yes for initial math, bounded reads, batching and parameterized revision. The saved tower skill changed dimensions in one invocation. Plan around the guest's call, time and output limits. |
| 9 | **How far with existing tools?** Survey, explicit-coordinate primitives, screen inspection, patterns, generated shape commands, saved skills, schematic exchange and partial revisions already work. An external TypeScript layer can calculate seeded materials and coordinate differences offline. Re-reading blocks via separate calls cannot guarantee atomicity. |
| 10 | **Which features need native integration?** Strong compare-and-commit, authoritative events, native ghost previews and independent rendering need a game-side facility. Try existing mod APIs or a second camera client before adding a companion. Chat polling, geometry, palette management and the project database can stay outside the game. |
| 11 | **Build first.** An addressed chat loop for one player, one world, one selected site and one reversible revision. Use the existing tower skill, show the silhouette and estimated change count, and recheck manually edited cells before applying an approved change. |
| 12 | **Reuse.** Keep MCPFabric, WorldEdit and Axiom. Study MCB for its prompt queue and Litematica previews, the collaborative Paper project for conflict-checked edits, GDPC and Blockwright for terrain surveys, and Ashlar for region snapshots. Evaluate seeded simplex noise and Three.js curves externally. [Comparison](ecosystem.md) · [SDK design](architecture.md) |

## Smallest next phase

Limit the next milestone to a **single watchtower conversation**. Let the player point, ask for massing, approve it, place one distinctive block in Axiom and ask for a taller roof. End the test when Codex replies in-game, changes only the approved cells, preserves or reports the player's block, and can undo its own revision without touching later work. Use a disposable staging plot or schematic preview for this milestone. A persistent city object graph, a new MCP server, voice and a new renderer can wait until this loop feels good.
